Words before we need them

These terms often arrive in one dense sentence. That forces the audience to decode vocabulary while following the argument. Learn the concrete meaning first.

WebAssembly or Wasm
A binary instruction format that a browser or another host can load, check, compile, and run. The file contains operations such as integer addition and memory load. It does not contain a browser or operating system.
Emscripten
A compiler toolchain. It uses Clang to compile C or C++ and produces Wasm plus JavaScript support code. That support code loads the module and translates useful JavaScript values into the lower-level forms C and C++ expect.
LLVM
A shared compiler infrastructure used by Clang and many other language tools. In this story it is the middle of the pipeline between C++ source and the final JavaScript or Wasm output.
ABI
Application Binary Interface. It is the low-level agreement about function names, argument types, return types, memory layout, and ownership. If JavaScript passes a pointer but C++ expects a copied string, the two sides disagree on the ABI.
Linear memory
A numbered row of bytes. Address 0 is the first byte, address 1 the second, and so on. C and C++ pointers become numeric offsets into this row.
Host
The program that runs the Wasm module. In this talk the host is the browser and its JavaScript engine. Wasm can also run in servers and command-line runtimes.
Binding or glue
Generated or handwritten adapter code that turns a JavaScript string, array, or object into values that a compiled function can accept, then converts the result back.
API
Application Programming Interface. A named set of functions and value shapes that one piece of code offers another.
CPU
Central Processing Unit, the processor that executes instructions. "CPU time" means time spent actively computing instead of waiting for input.
Typed array
A JavaScript view that reads an ArrayBuffer as fixed-width elements. Uint8Array reads unsigned bytes; Int32Array reads signed 32-bit words.
Pointer
A number used as a memory address. In Wasm linear memory it is normally a byte offset, not a JavaScript object reference.

A rule for the room

"Whenever I say boundary, I mean the exact moment a value moves between JavaScript's object world and WebAssembly's typed values or byte memory."

The whole story in five minutes

A toy language for a tiny robot

JavaScript is a friendly shopkeeper. You can hand it many kinds of things and it works out what you meant. C++ is a factory blueprint. Every box has a size, every shelf has an address, and the instructions assume those details will not change. Emscripten first taught the shopkeeper to imitate the factory by using odd signals such as |0. Browsers learned those signals. WebAssembly replaced the imitation with a small robot language that states the sizes and operations directly.

The precise version matters. WebAssembly is a portable instruction format. "Portable" means the same module format can run on different processors because the host compiles it for the current machine. Its values state their widths, such as 32-bit integer or 64-bit float. Its loops and branches must form valid nested blocks, which is what "structured control flow" means. Imports are functions or objects supplied from outside. Exports are functions or objects made available to the host. Linear memory is a bounded row of bytes that the module can read and write. JavaScript usually loads the module, supplies browser functions, and updates the Document Object Model, or DOM, which is the browser's in-memory representation of the page.

C or C++ source | Emscripten and Clang v Wasm module (.wasm) ---- exports ----> JavaScript | | +---- linear memory bytes <---- typed-array views | DOM, fetch, canvas

The thesis

"WebAssembly is an explicit machine contract hosted by JavaScript. The hard part is rarely adding two integers. It is deciding the representation, copy, owner, and lifetime whenever data crosses the boundary."

Why the number quiz works

Hexadecimal writes numbers with sixteen digits, 0 through 9 and a through f. Each f represents four one-bits, so 0xffffffff is thirty-two one-bits. Those bits have no sign by themselves. An operation chooses how to read them. JavaScript Number reads the literal as positive 4,294,967,295. A bitwise operation first converts it to a signed 32-bit integer. In two's-complement signed representation, thirty-two one-bits mean -1. A Uint32Array reads the same bits as an unsigned integer, so it returns the positive value.

const bits = 0xffffffff;
console.log(bits);                       // 4294967295
console.log(bits | 0);                   // -1
console.log(new Uint32Array([bits])[0]); // 4294967295
console.log(new Int32Array([bits])[0]);  // -1

IEEE 754 binary64 is the standardized 64-bit layout used for a JavaScript Number. It stores a sign, an exponent that sets scale, and significant binary digits. It represents every integer exactly from negative 2^53 - 1 through positive 2^53 - 1. Past that safe range, adjacent integers can round to the same Number. Bitwise operators temporarily impose a 32-bit conversion. Typed arrays impose a fixed-width interpretation on stored elements. BigInt stores integers of whatever size available memory permits, but it is a different JavaScript type and does not mix freely with Number arithmetic.

Accuracy trap

Do not say "JavaScript has only floating-point numbers, so it cannot represent integers." It represents a large range of integers exactly. Say that Number does not carry a distinct fixed-width integer type.

Wrapping

Wasm i32.add keeps only the low 32 bits of the mathematical result. That is wrapping modulo 232: after 4,294,967,295 comes zero. Comparison and division have separate signed and unsigned instructions because those operations need an interpretation. In C++, the language guarantees this wrap for unsigned integers. Signed overflow is undefined behavior, which means the C++ standard imposes no required result and the optimizer may assume it never occurs. Use uint32_t when the example promises wrapping before it is compiled to Wasm.

uint32_t add(uint32_t a, uint32_t b) { return a + b; }

;; the same idea in WebAssembly text format
(func (export "add") (param i32 i32) (result i32)
  local.get 0
  local.get 1
  i32.add)

asm.js: types written as punctuation

Emscripten originally compiled LLVM's intermediate compiler instructions into JavaScript. C and C++ programs assume that a 32-bit integer wraps in specific cases, arrays occupy adjacent bytes, and a pointer names a memory address. Ordinary JavaScript does not state those promises in its syntax. asm.js solved the mismatch by allowing only a carefully chosen subset of JavaScript and requiring repeated coercion patterns. "Statically checkable" means the engine could verify those patterns before running the function instead of guessing types from live values.

function add1(x) {
  x = x | 0;          // parameter is treated as int32
  return (x + 1) | 0; // result wraps to int32
}

The first |0 is a type annotation disguised as a normal coercion. That compatibility trick was clever and costly. Browsers still parsed source text, compiler intent lived in idioms, and new machine features had to remain valid JavaScript.

A secret handshake

The compiler wrote legal JavaScript but repeated a secret handshake. A browser that knew it could prepare the code like machine code. A browser that did not know it still followed the longhand instructions.

asm.js proved that large native codebases could reach the web and that browser vendors could agree on a better compilation target. The 2015 WebAssembly announcement described an evolutionary path beyond asm.js, not a hostile replacement for JavaScript.

The machine you should picture

A module is the compiled, reusable definition. It can contain functions, mutable or immutable global values, tables, memories, and declarations of what enters or leaves the module. An instance is one live copy of that module with its imports connected and its mutable state created. Two instances of one module can have different memories, just as two objects created from one class can hold different fields.

At the JavaScript boundary, i64 uses BigInt because Number cannot exactly carry every 64-bit integer. Passing a Number where i64 is expected throws. SIMD means one instruction performs the same operation on several packed numbers, useful in image and audio loops. Wasm threads use shared memory and require browser security headers that isolate the page from other origins. Reference types let Wasm hold restricted references instead of encoding everything as numbers. These features are real, but the demo uses the ordinary Emscripten C/C++ agreement: scalar values and bytes in linear memory.

Instantiation

const imports = { env: { log_i32: value => console.log(value) } };
const result = await WebAssembly.instantiateStreaming(
  fetch("kernel.wasm"), imports
);
result.instance.exports.run();

fetch requests the compiled file. instantiateStreaming validates and compiles bytes while they arrive, then creates an instance using the supplied imports. MIME type is the HTTP response label that tells the browser what kind of bytes arrived; Wasm should use application/wasm. Opening a page through file:// does not provide normal HTTP responses and origin rules, so serve the repository over HTTP for the demo.

The boundary: representation, copy, owner, lifetime

"Representation" asks which bits stand for the value. "Copy" asks whether bytes were duplicated or merely viewed. "Owner" names the code responsible for releasing storage. "Lifetime" says the interval during which an address or view still points to the intended data. These four words are a debugging checklist, not architecture jargon.

JavaScript heap WebAssembly linear memory strings, arrays, objects bytes at numeric offsets GC chooses lifetime C/C++ allocator chooses lifetime | | +-- scalar value --------------------->| +-- copy into allocated bytes -------->| +-- typed view onto memory.buffer -----+

GC means garbage collection. JavaScript finds objects that can no longer be reached and eventually reclaims them. C and C++ code compiled by Emscripten commonly uses malloc to reserve bytes and free to return them. JavaScript's collector does not see those C++ ownership rules.

Scalars

A scalar is one value rather than an array or object. Small numeric arguments travel directly according to the function signature. An i32 crossing to JavaScript appears as Number. An i64 appears as BigInt. A C++ Boolean or enum may become a number or a friendlier JavaScript value depending on which binding code was generated, so check that binding rather than assuming.

Strings

A JavaScript string stores text in the engine's own representation. A typical C string is a sequence of UTF-8 bytes followed by a zero byte that marks the end. UTF-8 is a rule for turning Unicode text into bytes. The adapter measures those bytes, reserves enough linear memory, writes the bytes and final zero, calls C++, and releases temporary storage. A returned pointer is only a numeric address. JavaScript still needs to know where the text ends and which side must release the bytes.

const length = new TextEncoder().encode(name).length + 1;
const ptr = Module._malloc(length);
Module.stringToUTF8(name, ptr, length);
try {
  Module._greet(ptr);
} finally {
  Module._free(ptr);
}

Image buffers

RGBA means four one-byte channels per pixel: red, green, blue, and alpha transparency. A 100 by 50 image therefore needs 100 * 50 * 4 = 20,000 bytes. HEAPU8 is Emscripten's unsigned one-byte view over Wasm memory. Reserve those bytes, copy the image into the reserved range, call one function that processes the entire image, then copy the result back if canvas or other JavaScript code needs an independent copy. "Coarse call" means one call does substantial work. It is the opposite of crossing the boundary once for every pixel.

const bytes = imageData.data;
const ptr = Module._malloc(bytes.byteLength);
try {
  Module.HEAPU8.set(bytes, ptr);
  Module._grayscale(ptr, width, height);
  bytes.set(Module.HEAPU8.subarray(ptr, ptr + bytes.byteLength));
} finally {
  Module._free(ptr);
}

Stale views after growth

A typed array view points at a particular memory.buffer. When memory grows, the engine can replace or detach that buffer. Recreate cached views after growth. Embind memory views have pointer-like lifetime; the runtime does not keep the C++ allocation alive for you.

A hotel claim ticket

A pointer is a room number, not the suitcase. If the hotel expands or someone checks out, yesterday's room number may no longer lead to your suitcase. A typed-array view is a window into those rooms. It does not own what it sees.

A binding saves handwritten conversion code. It does not make memory self-owning. An Embind object handle may need .delete(), which calls the C++ destructor and releases its allocation. A memory view can "dangle," meaning it still exists in JavaScript after C++ has freed or reused the bytes it points at. Prefer one function that processes a complete value or buffer and document who releases every returned object.

The four-question habit

"For every crossing, ask what the representation is, whether we copied it, who owns it, and how long it remains valid. If the API cannot answer all four, the binding is unfinished."

When WebAssembly helps

"Compute-heavy" means CPU time is spent repeating arithmetic or byte operations, not waiting for a network response or changing page elements. An image kernel applies one algorithm to many pixels. A codec turns compressed media into playable data or back again. A parser turns source bytes into a structured result. CAD means computer-aided design, where geometry can require large numeric workloads. These are candidates because they do substantial work per call or reuse an existing native library.

Measure the complete operation. Start the clock before JavaScript prepares or copies input. Stop it only after the result reaches the consumer that needs it. Include module loading on first use, wrapper work, allocation, memory copies, and the compiled operation. A fast grayscale loop can still lose if JavaScript calls Wasm separately for each pixel.

Evidence Wasm may helpEvidence to stay in JavaScript
A profile, which is a timed breakdown, shows most CPU time inside one numeric loop.Most time is waiting for network data or recalculating page layout.

A tested C or C++ library already implements the hard part.The feature mostly reads and changes DOM elements.

Claims to refuse

"Near-native" has no universal ratio. Browser, CPU, compiler options, algorithm, input size, and boundary work all change the result. Wasm prevents a module from reading outside its assigned linear memory, but it does not repair a wrong algorithm. An invalid memory access can trap, which stops execution. A program can still exhaust memory or preserve an unsafe-language mistake inside its permitted byte range.

Rehearsal, checks, and Q&A

  1. Run the 0xffffffff quiz before explaining the contracts.
  2. Use |0 as the thread from coercion through asm.js to explicit i32.
  3. Draw the two memory worlds. Point to every allocation, copy, view, and free in the demo.
  4. End with the four questions, not a speed claim.

Self-test

Why can the same 32 bits mean -1 or 4,294,967,295?

Signedness is an interpretation applied by an operation or view. The word is identical.

Why does i64 use BigInt?

Number cannot represent the full 64-bit integer range without loss.

What breaks a cached HEAPU8.subarray?

Freeing or reusing its allocation invalidates the data. Memory growth may replace the buffer.

Why is one call per pixel poor interop?

Repeated boundary overhead can dominate the arithmetic. Process a region per call.

Can core Wasm access the DOM?

No. The host supplies JavaScript imports or generated glue.
