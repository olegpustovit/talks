Model answers

10 points

1. One word, three readings

The outputs are 4,294,967,295, then -1, then 4,294,967,295, then -1. The hexadecimal literal becomes a JavaScript Number. The bitwise OR converts that Number to a signed 32-bit integer. Thirty-two one-bits are -1 under two's-complement interpretation. Uint32Array stores the low 32 bits and reads them without a sign. Int32Array reads the same bits as signed. Neither reading is the sole real value. The word contains bits; the operation or view supplies interpretation.

  • 4 points for all outputs.
  • 4 for explaining conversion and typed views.
  • 2 for separating bits from signedness.
10 points

2. Audit a wrapping function

Adding one to the maximum int32_t value overflows a signed C++ integer. The C++ standard leaves signed overflow undefined, so the compiler may optimize under the assumption that it never occurs. Use uint32_t add_one(uint32_t x) { return x + 1u; }. Unsigned addition wraps modulo 232. The exported Wasm result has type i32. JavaScript receives a Number produced from the 32-bit word, and the direct JS boundary convention reports a word with its top bit set as a negative signed Number. If the application wants 0 through 4,294,967,295, apply result >>> 0 or store through a Uint32Array.

  • 4 points for C++ undefined behavior.
  • 3 for an unsigned implementation.
  • 3 for boundary interpretation.
10 points

3. Why asm.js mattered

In ordinary JavaScript, |0 converts its operand through the bitwise integer rules and returns a signed 32-bit Number. In an asm.js function, assigning x | 0 back to x also states that the parameter is used as an integer. A supporting engine validates the restricted function and compiles it before hot execution. The syntax remains legal JavaScript, so an engine without asm.js support performs the ordinary coercions. The cost is that machine intent is encoded as punctuation in a large source file. Wasm states i32 and i32.add directly in a compact binary.

  • 3 points per requested level.
  • 1 for fallback compatibility.
10 points

4. Module, instance, memory, table

The module is the compiled definition. Each instance creates its own globals, tables, and memories unless imports connect it to shared objects. Two instances can therefore have separate state, or both can import the same WebAssembly.Memory. A table is an indexed list of references used by indirect calls and related reference operations; it is not byte storage. Core Wasm has no built-in DOM instruction. JavaScript must import a function that performs the DOM operation, or generated glue must call JavaScript on the module's behalf.

  • 4 points for module and instance state.
  • 3 for shared memory through imports.
  • 3 for table and DOM explanation.
10 points

5. Find the stale view

The view does not own the histogram allocation. After _free(ptr), the allocator can reuse those bytes while the view object still exists. Separately, _process_large_image may grow Wasm memory. Growth can replace the underlying ArrayBuffer, leaving a previously created view detached or tied to the old buffer.

const ptr = Module._make_histogram();
try {
  Module._process_large_image(imagePtr, imageLength);
  const current = Module.HEAPU32.subarray(ptr / 4, ptr / 4 + 256);
  const histogram = new Uint32Array(current); // stable JS-owned copy
  consume(histogram);
} finally {
  Module._free(ptr);
}

This assumes the processing call does not itself free or relocate the histogram allocation. A stronger API would return the histogram after processing or fill a caller-provided output range.

  • 3 points per hazard.
  • 3 for recreating the view and copying before free.
  • 1 for questioning the native allocation contract.
10 points

6. Design the image API

Choose gray_image. A 24-megapixel RGBA image has about 96 million bytes. One call can process a tight loop. The per-pixel API causes roughly 24 million boundary calls and cannot see neighboring pixels if the algorithm later changes. JavaScript checks that width and height are positive integers and that expected bytes equal the supplied length. C++ performs the size calculation in size_t with an overflow check before multiplication. JavaScript allocates the Wasm range, copies input once, calls once, copies output once when Canvas needs JS-owned bytes, and frees in finally. Benchmark allocation, both copies, the call, kernel time, and final canvas upload for representative image sizes. Compare against optimized JavaScript and test cold module load separately.

  • 2 points for the coarse API.
  • 4 for boundary and validation detail.
  • 2 for ownership and cleanup.
  • 2 for full-path measurement.
10 points

7. Strings without hand waving

Encode the Unicode string as UTF-8. Do not use JavaScript character count as byte count because Ž and the emoji require multiple bytes. Compute encoded byte length, add one for the C zero terminator, allocate that many bytes, write UTF-8 plus zero, call the C function, then free the bytes in finally. The pointer remains valid only until free or a conflicting memory action. A function accepting const char * may read but not modify through that pointer; const does not promise that it will not retain the address. It may retain it only if the API explicitly says so. In that case the allocation must outlive later use, and the contract needs a matching release function or a native copy.

  • 4 points for encoding and sizing.
  • 3 for lifetime and cleanup.
  • 3 for the retention contract.
10 points

8. Pick an interop layer

Use raw exports or cached cwrap functions for the four hot numeric DSP calls. Their scalar contract is small and avoids class wrappers in the hot path. Use Embind for the stateful C++ class if a natural JavaScript object is worth its glue size. Document that every constructed handle needs .delete(), or wrap it in an application object with explicit disposal. A fully raw class API is also valid if bundle size dominates, but then expose create, operate, and destroy functions and test invalid handles. Measure call frequency before choosing convenience over a narrow ABI.

  • 4 points for a reasoned mixture.
  • 3 for destruction and handles.
  • 3 for wrapper size and hot-call analysis.
10 points

9. Reject a weak benchmark

The benchmark excludes download, compilation, instantiation, and input conversion. One run is vulnerable to timer noise and JavaScript JIT warm-up. Fibonacci may use different algorithms, recursion costs, integer semantics, or overflow behavior. The input may be too small, and the result may be unused, allowing optimization. Test equivalent algorithms and numeric contracts over representative inputs. Warm each implementation when measuring steady state, run many randomized samples, consume results, and report distributions rather than one ratio. Measure cold load separately. Include boundary copies for the production data shape. Test in target browsers and devices. The decision should use end-to-end latency, throughput, memory, download size, and build cost.

  • 5 points for threats.
  • 5 for a reproducible decision-oriented design.
10 points

10. Architecture decision

Do not rewrite the dashboard in Rust. At most 8 percent of current time is JavaScript, so even deleting all JavaScript execution would leave 92 percent. First inspect slow network requests, caching, payload size, request parallelism, server response time, layout invalidations, and oversized DOM trees. Record a user-centered trace such as interaction latency and identify the exact long tasks. Reconsider Wasm only if later profiling finds a stable CPU-heavy kernel with large inputs, such as local data decoding or geometry, and a prototype beats optimized JavaScript after including load and copies. The form and DOM code should remain in JavaScript because Wasm needs host calls to touch the page.

  • 3 points for rejecting the rewrite from the numbers.
  • 4 for the investigation plan.
  • 3 for concrete reconsideration evidence.
