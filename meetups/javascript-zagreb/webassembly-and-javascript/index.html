It historically had no distinct, general-purpose integer numeric type.

ECMAScript Number specification
Do not repeat the common claim that JavaScript cannot represent integers. The missing feature was an explicit machine-width arithmetic contract.
A different kind of overflow

Two integers become one Number.

const max = Number.MAX_SAFE_INTEGER;

max + 1  // 9007199254740992
max + 2  // 9007199254740992

(max + 1) === (max + 2)  // true

This is precision loss at 53 bits. It is not 32-bit wraparound.

Keep the two problems separate. Safe integer precision and fixed-width machine overflow are related to the talk, but they have different semantics.
A tiny operator with a second job
|0

Bitwise OR became a type annotation.

3.9 | 0          // 3
0xffffffff | 0   // -1
(x + y) | 0     // wrap to i32
ECMAScript ToInt32
ToInt32 truncates, reduces modulo 2^32, and interprets the high half as negative. This existing behavior gave compiler authors an opening.

Can you read the compiler's accent?

Valid JavaScript. Hidden types.

function add1(x) {
  x = x | 0;           
  return (x + 1) | 0;  
}

To a normal JS engine these are coercions. To an asm.js validator they are type declarations.

asm.js specification
Reveal the two annotations. `x | 0` makes the parameter's type visible at function entry. The result coercion keeps two's-complement 32-bit addition.
Why this generated code mattered

The asm.js contract

Compiler promises

  • restricted JavaScript syntax
  • visible types and coercions
  • one typed-array heap
  • predictable calls

Engine can do

  • validate at parse time
  • compile ahead of execution
  • keep values unboxed
  • skip repeated type checks

If validation fails, it is still JavaScript and can run through the ordinary engine.

Compatibility was the clever part. asm.js was generated code with a fast path, not a style people were expected to write by hand.

Original WebAssembly announcement
The original announcement called Wasm the next evolutionary step from asm.js. Existing Emscripten users were expected to switch targets rather than rewrite their programs.
A useful definition

WebAssembly is a typed instruction format.

Portable

The same module targets different CPUs and hosts.

Compact

A binary encoding is designed for transport and decoding.

Validated

Types, control flow, and indices are checked before execution.

Sandboxed

Linear-memory access is bounds-checked by the runtime.

It is not the visitor's native assembly, and it is not a JavaScript replacement.

WebAssembly high-level goals
"Typed instruction format" is more useful than "assembly for the web." The host compiles or interprets it and controls its capabilities.

A division of labor

JavaScript hosts the module.

  • module loading
imports⇄exports
WebAssembly
  • compiled kernels

Wasm gets browser capabilities through its host. A core module has no direct DOM API.

The design goal is synchronous calls in both directions. Most web applications should keep web orchestration in JavaScript and move bounded work into compiled modules.

C++ · deliberately boring

Mutate bytes in place.

extern "C" EMSCRIPTEN_KEEPALIVE
void posterize(uint8_t* pixels,
               size_t length,
               uint8_t levels) {
  for (size_t i = 0; i + 3 < length; i += 4) {
    pixels[i]     = quantize(pixels[i], levels);
    pixels[i + 1] = quantize(pixels[i + 1], levels);
    pixels[i + 2] = quantize(pixels[i + 2], levels);
  }
}

The alpha byte stays untouched. The boundary contract is pointer, byte length, and levels.

Do not sell the loop as advanced C++. Its simplicity lets the room account for all the data movement.
JavaScript · account for every byte

Allocate. Copy. Call. Copy. Free.

const ptr = Module._malloc(rgba.byteLength);

try {
  Module.HEAPU8.set(rgba, ptr);                  // copy in
  Module._posterize(ptr, rgba.byteLength, 6); // one call

  const out = Module.HEAPU8.slice(
    ptr, ptr + rgba.byteLength
  );                                             // copy out
} finally {
  Module._free(ptr);                             // owner frees
}
Say the verbs in the title as each line appears. `slice` is intentional because the result must survive `_free`.
One API choice changes lifetime

Copy or view?

HEAPU8.slice(start, end) Independent copy
  • cost grows with buffer size
  • safe after `_free`
  • safe after memory growth
HEAPU8.subarray(start, end) Shared view
  • cheap to create
  • invalid after free
  • may detach after memory growth

"Zero-copy" is a lifetime promise, not a free speed sticker.

A view is useful when the consumer can finish before mutation, deallocation, reallocation, or memory growth. Otherwise copy deliberately.
A bug that looks impossible

Memory grew.
Your old view did not.

let view = Module.HEAPU8.subarray(ptr, ptr + length);

Module._operation_that_might_allocate();

// Refresh after a possible WebAssembly.Memory growth.
view = Module.HEAPU8.subarray(ptr, ptr + length);

Emscripten refreshes its canonical HEAP views. It cannot refresh the views you already captured.

Emscripten memory access guide
This matters when ALLOW_MEMORY_GROWTH is enabled. A growth can replace the backing ArrayBuffer. Recreate derived views after calls that may allocate.

Use WebAssembly where it fits

Use it when it earns the boundary.

Good fit

  • valuable C, C++, or Rust library
  • large numeric or media kernels
  • portable sandboxed computation
  • data can stay in linear memory

Keep it in JavaScript

  • DOM-heavy application logic
  • small work with chatty calls
  • objects constantly cross the boundary
  • no measured user-facing problem
Existing libraries and coherent compute kernels are the strongest web use cases. A normal business form is not waiting for a C++ rewrite.
